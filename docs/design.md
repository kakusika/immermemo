# Immermemo の設計

このドキュメントは、アプリ全体としての仕組みを説明する。各Rustクレートの実装の中身（木構造をどう比較するか、等）はそこに書かない――それは`core/sync`・`core/merge`それぞれの`src/lib.rs`冒頭のコメントに書いてある。ここに書くのは「そもそも全体としてどう動くか」だけ。

## これは何をするアプリか

スマホで使う、ふつうのメモアプリ。書いたメモは自動で他の端末（もう1台のスマホ、PCなど）にも反映される。

## 全体の仕組み：サーバーは必ず1つ、端末同士は直接話さない

これはP2P（端末同士が直接通信する仕組み）ではない。

```
端末A ──(送る)──▶ サーバー ◀──(受け取る)── 端末B
```

サーバーは、GitHubでも自分で立てたGiteaでも、自前で用意したgitサーバーでもいい。重要なのは「サーバー側には特別なプログラムを何も書かない」こと。普通のgitのpush/pullがそのまま通じる、ただのgit置き場として使う。合体（マージ）の判断は全部端末側でやる。サーバーは「預かって、渡すだけ」。

これを選んだ理由は、そもそもの出発点が「gitを使って同期したい」だったから。サーバー側に独自の判断ロジックを書き始めると、それは「gitを使う」ではなく「gitを内部で使う自前サービスを作る」になってしまい、話が変わる。

## gitの中に何を入れるか：文章だけ。添付ファイルは入れない

gitは文章の履歴を持つのにはとても向いている（何年書き溜めても数十MB程度で済む）が、画像などのバイナリファイルの履歴を持つのには向いていない（同じ画像を貼り直すたびに、その画像がまるごと履歴に溜まっていく）。

なので：

- メモの文章（`.tmt`ファイル）だけをgitに入れる。
- 画像・添付ファイルはgitに入れず、別の置き場（サーバー上のファイル置き場）に置く。メモからは「このファイルを指している」という印だけを持つ。

これにより、「履歴が肥大化するから古い履歴を間引く」といった複雑な仕組みを別途作らずに済む。gitの中身は最初から一生軽いままにしておく、という考え方。

## 同期の流れ（1回の同期でやっていること）

1. **書く** -- ただのファイル保存。この時点ではまだgitは関係ない。
2. **端末の中だけでコミットする** -- 同期のタイミング（アプリを開いた時、一定時間おき、など）で「今の状態」を端末のローカルな履歴に記録する。まだネットワークには繋いでいない。
3. **サーバーの様子を見に行く（フェッチ）** -- サーバーの方が自分より進んでいないか確認する。
4. **合体させる（マージ）** -- サーバーの方が進んでいたら、「前回サーバーと一致していた時点」「自分がその後した変更」「サーバー側でその後起きた変更」の3つを突き合わせて1つにまとめる。自動でまとめきれない部分だけ、メモの中に「両方の内容」を残す印をつける。この時点ではまだ何もサーバーに送っていない。
5. **サーバーに送る（push）** -- まとめ終わった結果をサーバーに送る。もし送る直前に別の端末が先に送っていて弾かれたら、3に戻ってやり直すだけ（これは普通のgitがそのままやってくれる動き）。
6. **本人に見せる** -- 4で印がついたメモがあれば、次にその本人がそのメモを開いた時に「ここ、両方あるので選んでください」と表示する。選んだ結果は、また2のコミットとして扱われる。

サーバーが判断することは何もない。「合体できるかどうか」「合体できない部分をどう見せるか」は全部端末側の仕事で、サーバーに送る前に済ませておく。

## まだ決まっていないこと

- 添付ファイルの置き場（サーバー上のどこに、どういう形式で置くか）はまだ決めていない。
- 同期のタイミング（アプリを開いた時／一定間隔／手動のみ）の具体的な間隔・トリガーはまだ決めていない。
- 衝突が残ったメモを開いた時の実際の画面（UI）はまだ決めていない。
- 自前サーバーを選んだ場合の、実際の運用・鍵管理の手順はまだ決めていない。

これらは、それぞれ着手する段階で改めて詰める。
